## What failed, in order

1. Earlier sponsored Play failures stopped before a provider call when the optional project cost cap was unset. The code did not pass a per-call estimate to the global sponsored allowance ledger. The resulting UI said the shared call budget was exhausted. The current branch now reserves the model estimate against the global allowance even with no project cap, and serializes sponsored portfolio dispatch within a session. This diagnosis and fix are recorded in `docs/STATUS.md` under “Sponsored unlimited-cost session reservation.” It requires independent verification against a successful provider call.
2. The local Session 6 investigation exposed a different bug: a ChatGPT plan/app usage-limit rejection was treated as an unknown-cost attempt, leaving a $0.225765 sponsored allowance hold. SIGMA then attempted the remaining strategies, which were denied by SIGMA's cumulative allowance. The current branch classifies known usage-limit rejections as zero-usage, releases the reservation, and stops further dispatch. The local hold was corrected separately; that ledger change is local operational state and is not in the PR. The Session 6 original record is not present in the exported project artifact, so this point is based on the previous local diagnosis and `docs/STATUS.md`, not the attached project export.
3. Session 7, recorded in the attached export, ended with **0/30 calls**. All five investigator steps show `failure_kind=budget_denied`, `attempt_status=not_dispatched`, and estimated reserves around $0.2265–$0.2269. Each event says the cumulative cloud research allowance had been reached. This is consistent with the earlier held reservation, though the export alone cannot prove the exact ledger balance at Session 7 admission.
4. After the local ledger correction, Session 8 reached the provider. It was sponsored, `mode=chatgpt`, model `gpt-6.1-sol`, call limit 30, no project session-cost cap, and one investigator call was attempted. That call reserved **$0.213035** and 91,377 tokens. It ended `failure_kind=provider_limited`, `attempt_status=provider_rejected`, with no saved strategy or research artifact. SIGMA emitted `provider.usage_limit`, stopped the remaining strategies, and released the reservation. The local SQLite `calls` row for this session is `status=usage_estimated`, `amount_usd=0.0`, `token_reservation=0`, and null input/output usage. These facts show the user-visible $0.25 SIGMA allowance was enough to admit this call and was not spent on the rejected attempt. They do **not** show that the ChatGPT sponsor account had unused plan/app capacity.

## Distinct limits and the misleading HTTP label

The $0.25 pill is the signed-in member's **SIGMA sponsored allowance**. It controls SIGMA's own pre-dispatch reservation ledger. The sponsored ChatGPT request uses the designated sponsor ChatGPT account, not the signed-in member's personal ChatGPT account (`docs/GETTING_STARTED.md`, `src/sigma/cloud_sponsor.py`). Its plan/app limit is separate. A $0.25 SIGMA allowance can coexist with a provider usage-limit rejection; Session 8 demonstrates that distinction. We have no provider account telemetry or raw provider response in the PR, so we cannot determine whether the limit is account-wide, app-specific, model-specific, temporary, or policy-driven.

Session 8's saved step says `provider_http_status=400`, but `sponsor-diagnostics.log` recorded `sponsor_inference status=call_started`, `request_attempted`, `http_200`, then `response_invalid` at 16:58:11–16:58:13 UTC. This is consistent with an outer HTTP 200 stream that carried a provider error event. `src/sigma/plan_stream.py` maps `subscription_sharing_usage_limit_exceeded` to the displayed limited message and converts streamed `error`/`response.failed` events through `failure(400, ...)`. Thus the displayed “HTTP 400” appears to be SIGMA's synthetic normalization of a streamed failure, **not proof of an HTTP 400 transport response**. The generic `response_invalid` diagnostic hides the recognized provider-limit classification. The exact streamed event and provider account-side cap still require provider-side evidence.

## What is fixed, and what is still unverified

The current branch addresses the zero-call missing-estimate path and the incorrect retained allowance hold for known provider-limit rejections. Session 8 is evidence that the reservation was released and no fallback occurred. It is **not** a successful research session. No further provider calls should be made automatically after a plan/app limit. There has been no automatic switch to API-key billing or to a personal account; those require explicit choices. Hosted personal ChatGPT authorization remains disabled pending OpenAI's hosted integration requirements.

The coordinator should check the designated sponsor account's official usage/authorization telemetry for the Session 8 time, determine the actual plan/app cap and whether the requested model and integration route are eligible, and decide whether the sponsored provider configuration can reliably support a 30-call investigation. If a separately billed service key is proposed, it needs explicit operator configuration and reviewed billing limits; SIGMA must never silently fall back. The UI should distinguish “SIGMA allowance remaining” from “ChatGPT plan/app capacity unavailable.” The provider diagnostic should retain the streamed error category and avoid claiming a transport HTTP 400 when the transport was 200. A successful, bounded real-provider session is still needed before calling the Play experience shippable.

No live provider calls, paid calls, credential changes, or hosted configuration changes were made while preparing this writeup. No direct communication with another Codex worker occurred.
