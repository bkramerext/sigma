## Corrections and architecture

- `src/sigma/session_log.py`: replaced the single process-wide writer queue with independently ordered per-session queues. Append, scan, redaction, locks and `fsync` all run on writer threads. Reads no longer join any writer queue; they synchronize only on the requested file and its project deletion guard. Project deletion prevents new project log work, drains only that project's queues, waits for active readers, then removes its log tree. Torn frames are skipped read-only and retained byte-for-byte; later frames append after them.
- `src/sigma/research_sessions.py`: after existing strict Investigator output validation, the isolated logger receives project title/problem and the validated AI claim. It persists a 2–4-word subject phrase only when that contiguous phrase appears in both project context and the claim. This adds no schema field or provider request. If there is no corroborated phrase yet, the read window shows a deterministic, title-derived display fallback. Once the validated subject name is persisted, later sessions reuse it.
- `frontend/src/SessionLogPage.tsx`: polling remains recursive and single-flight; cursor advancement is monotone and event sequence IDs are deduplicated, including backend replay.
- `tests/session_log.py`: delayed writes, independent-session reads, concurrent append ordering, read/deletion race, append-only recovery, multiline content, redaction, failure isolation, naming and cleanup.
- `tests/research_sessions.py`: production provider-boundary request/response capture and validated-claim naming with deterministic provider fixtures.
- `tests/cloud_research_api.py`, `tests/lifecycle.py`: owner/cross-user access, download, and project deletion with a queued session log.
- `browser_checks/issue301_session_log.py`: real Chromium popup/poll/download check with mocked API responses.
- `browser_checks/issue301_integrated.py`: Chromium polling against an HTTP fixture that calls the production log store.
- `browser_checks/issue301_full_app.py`: Chromium through a running Vite frontend and the actual SIGMA FastAPI log read/download routes and production store; creates a real temporary project/session, inserts deterministic request/response events, delays retrieval, and replays an event. No research or provider call is started.

## Acceptance status

### MET

- Per-session background queues preserve write order without making reads wait for unrelated session work. Delayed storage remains off the research path. Read/deletion and active-project cleanup are serialized safely within the process.
- Markdown writes are append-only. Recovery never truncates or rewrites; tests preserve the interrupted bytes across restart and append later complete events.
- Frontend polling cannot overlap; delayed responses and duplicate event replay are checked in both storage-backed and full-FastAPI Chromium flows.
- Existing owner authorization and cross-user denial, secret redaction before persistence, project export isolation, session request/response capture and cleanup regressions pass.
- Context-grounded AI-claim subject matching yields the representative scientific, mathematical and general names above without changing response validation or adding a provider call. Stable assigned names are persisted and reused.

### UNMET

- None identified after this correction pass.

### UNVERIFIED / limitations

- Naming is conservative lexical corroboration, not semantic model-generated labeling: it uses a short contiguous project phrase only when the existing validated Investigator claim repeats it. If the claim paraphrases the subject without shared terms, the display uses the deterministic title fallback. No broad live-model naming quality evaluation was made; the fixtures establish the listed examples and reject generic lead-ins.
- The full-app browser test exercises actual frontend, FastAPI routes, authorization code path in local mode, and production store, with manually inserted deterministic events. It does not launch a live research session or contact a provider. Cloud cross-user authorization is covered separately through API tests.
- An abrupt process kill before queued events reach disk can lose those queued events. This is an explicit best-effort logging limitation; already-written data and interrupted trailing bytes are retained without mutation.
- The graph-present optional sandbox test remains skipped because its local image is unavailable.
