# T40 — Cloud account controls and real local Google administrator access

**Owner:** Red. **Status:** Assigned, not started. **Dependencies:** merged T22.2 authentication, T22.5 spending, T23.1 connection controls, and the local admin-preview implementation. **Scope:** Cloud UX and authenticated administration, not provider billing changes.

## Goal

Deliver the cohesive SIGMA account experience agreed during the first local cloud UI walkthrough. Preserve the existing copper/black design and connection-pill conventions, rather than adding a new account bar or standalone status cards. The same verified Google administrator must be able to access administrative controls when SIGMA is run locally or hosted; a fake `--admin` identity is not a substitute for real sign-in.

## Three permanent controls

1. **Google Sign-in pill**, visible in all modes. Compact status only. Clicking opens a minimalist Google account dialog with verified email and an *underlined* Sign out action. In mock mode, visibly identify the identity as simulated inside the dialog, not as a raw email in the header. Maintain normal sign-in, account switching, denial and sign-out behavior.
2. **ChatGPT connection pill**, **always visible**, including cloud and mock-cloud modes. Reuse the existing connection control, settings, and design. Place the current user's cloud inference allowance in this dialog as a **read-only** labelled remaining amount. Used/held figures may be present as secondary read-only detail, consistent with existing controls. A member cannot alter their allowance here; no billing fallback or claim that a Google account is a ChatGPT connection. In hosted mode, distinguish the SIGMA service-funded inference allowance from a personal ChatGPT plan.
3. **Administrator Settings** as a discreet **underlined link at upper left**, visible only to authenticated admins. Opens a dark/copper tabbed Settings dialog. The first and only required tab is **Access Management**; do not create empty placeholder tabs. Existing admin APIs enforce authorization independently of button visibility.

## Access Management

Preserve complete working functionality from T22.2/T22.5: exact email and domain rules, explicit email precedence, domain allowance **per authorized person**, admin/member roles, add/edit/revoke, durable estimated/held/remaining usage including revoked accounts, and audit records. Admin edits the USD spending allowance *here* (not in the ChatGPT dialog); default pilot amount $2, individually adjustable up to the $15 global cap. Reductions never erase charges or unknown holds. Keep role and spend permission checks on the server.

## Real Google account on localhost

- Provide an explicit local development route for **real Google OIDC sign-in** (not merely `--admin`). Support a registered loopback OAuth redirect and development-appropriate origin/cookie handling **without weakening hosted HTTPS, cookie, nonce, CSRF, ID-token, authorization, or workspace protections**. Never confer administrator privileges through a CLI flag, arbitrary email claim, or frontend mock.
- Document Google Cloud OAuth-client setup and a clear, safe local launch command. Keep `./sigma start` unchanged unless the user explicitly chooses real Google mode. Rename/introduce `--mock-cloud` for simulated mode, with `--admin` retained temporarily as a compatibility alias. Do not require real credentials for mock mode.
- **Bootstrap admin:** `SIGMA_CLOUD_BOOTSTRAP_ADMIN_EMAIL` is the operator's **actual Google account email**, supplied through protected configuration, not committed to the repo. On first verified login, the auth database binds that email to Google's immutable verified `sub` and grants `admin`; on subsequent logins require **both** matching email and bound subject. Bootstrap administrator cannot be revoked through ordinary Access Management. A nonmatching account must not inherit admin privileges.
- Local versus hosted state: a real local login must clearly indicate which administration target it operates on. **Do not claim local edits administer the hosted service if they only touch local SQLite.** For actual hosted administration from the local app, use a separately authenticated, HTTPS, server-authorized admin API/session against the hosted service (never direct remote SQLite/filesystem or copied cookies); if this secure routing is not implementable within this ticket, mark it UNMET and do not present a fake shared admin state. Preserve local SIGMA project behavior and cloud workspace isolation.

Existing connection/billing-mode status should make the active provider/funding route unambiguous; prefer a short inline hint or existing tooltip if a distinction needs explanation, not paragraphs, banners, or extra controls.

If personal ChatGPT access is unavailable in hosted mode, never imply it works, silently fall back to paid service inference, or describe the administrator-funded ChatGPT allowance as a charge to the user's personal subscription.

- **Visual acceptance:** the revised top-level Home and connection dialogs must be at least as restrained as the existing local UI, with no standalone funding boxes, duplicated status, dead-end buttons, or excessive text. Make reasonable layout decisions and inspect actual desktop/mobile screens before R4R.
