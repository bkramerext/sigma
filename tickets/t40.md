**Owner:** Red. **Status:** Assigned, not started. **Dependencies:** merged T22.2 authentication, T22.5 spending, T23.1 connection controls, and the local admin-preview implementation. **Scope:** Cloud UX and authenticated administration, not provider billing changes.

## Goal

Deliver the cohesive SIGMA account experience agreed during the first local cloud UI walkthrough. Preserve the existing copper/black design and connection-pill conventions, rather than adding a new account bar or standalone status cards. The same verified Google administrator must be able to access administrative controls when SIGMA is run locally or hosted; a fake `--admin` identity is not a substitute for real sign-in.

## Three permanent controls

1. **Google Sign-in pill**, visible in all modes. Compact status only. Clicking opens a minimalist Google account dialog with verified email and an *underlined* Sign out action. In mock mode, visibly identify the identity as simulated inside the dialog, not as a raw email in the header. Maintain normal sign-in, account switching, denial and sign-out behavior.
2. **ChatGPT connection pill**, **always visible**, including cloud and mock-cloud modes. Reuse the existing connection control, settings, and design. Place the current user's cloud inference allowance in this dialog as a **read-only** labelled remaining amount. Used/held figures may be present as secondary read-only detail, consistent with existing controls. A member cannot alter their allowance here; no billing fallback or claim that a Google account is a ChatGPT connection. In hosted mode, distinguish the SIGMA service-funded inference allowance from a personal ChatGPT plan.
3. **Administrator Settings** as a discreet **underlined link at upper left**, visible only to authenticated admins. Opens one broader dark/copper **Administrator Settings** dialog, with an existing-SIGMA-style tab bar and **Access Management** as its initial tab. The editable table and Add/Revoke/Save Updates controls belong **inside that tab**, not in a separate Access Management dialog. Do not create empty placeholder tabs. Existing admin APIs enforce authorization independently of button visibility.

## Access Management

Preserve complete working functionality from T22.2/T22.5: exact email and domain rules, explicit email precedence, domain allowance **per authorized person**, admin/member roles, add/edit/revoke, durable estimated/held/remaining usage including revoked accounts, and audit records. The administrator edits allowances here (not in the ChatGPT dialog); default pilot amount $2, individually adjustable up to the $15 global cap. Reductions never erase recorded charges or unknown holds. Server-side authorization and spending enforcement remain mandatory.

**Authorized entries presentation (required):**
- Replace the vertical list with a clean, compact **table**, matching SIGMA's copper/dark styling. Email addresses and domains must be legible, with high-contrast text; never use low-contrast green-on-black text. Show meaningful columns for **Email/domain**, **Role**, **ChatGPT allowance**, and **Actions**; only add spending columns if they remain readable without crowding. Preserve active/revoked distinctions and access to recorded spending.
- **New-entry row paradigm:** A small **+** inserts/reveals a new editable row inside the sorted table. Enter an email address or domain, select the permitted role, and type its allowance; an underlined **Add** action on that row creates the authorization. No separate add form above the table. Keep the table sorted alphabetically by email/domain after Add and after updates.
- Existing rows allow editing their **Role** (Member/Admin where valid) and **ChatGPT allowance** using compact select/currency inputs, never sliders. The role restriction forbidding domain administrators remains enforced.
- Edits to existing entries remain **draft changes locally** until saved. Show one **Save Updates** button only when any **existing** row's allowance or role differs from its last saved value; remove individual per-row Save allowance buttons. If a draft is invalid, show a local validation message and disable Save Updates until fixed. A no-op edit must not trigger an API call.
- Saving submits **only changed entries** through authenticated backend update operations. Prefer one atomic batch transaction/API for multiple changed allowances so the UI does not falsely report full success if one update fails. Preserve unsaved values and show a concise error on failure; refresh confirmed values on success and hide Save Updates when clean. Prevent accidental loss of unsaved edits on close or navigation.
- **Exactly two row actions:** underlined **Add** on new-entry rows and underlined **Revoke** on existing active rows. **Save Updates** is the one conditional dialog-level action for dirty allowance/role edits, not a row action.
- **Dialog conventions:** Administrator Settings is a tabbed dialog with Access Management as its only implemented tab. Place an underlined **Close** action directly after the dialog title. Do not show an X icon or Cancel button. **Close does not undo saved actions**. Underlined **Add** commits a new row immediately, and underlined **Revoke** commits revocation immediately after appropriate confirmation; each reports success or failure. Existing-row role/allowance modifications are staged until the single underlined **Save Updates** action at the bottom is used. It appears only when existing entries have valid, unsaved changes and disappears once saved. On Close with unsaved drafts, warn about discarding only those *unsaved edits*, without suggesting that already completed Add, Revoke, or Save operations can be rolled back. No filled primary save button.

- Check narrow/mobile layout and keyboard focus behavior: table may scroll horizontally or simplify responsibly, without unreadable truncation or misaligned row actions.

## Real Google account on localhost

- Provide an explicit local development route for **real Google OIDC sign-in** (not merely `--admin`). Support a registered loopback OAuth redirect and development-appropriate origin/cookie handling **without weakening hosted HTTPS, cookie, nonce, CSRF, ID-token, authorization, or workspace protections**. Never confer administrator privileges through a CLI flag, arbitrary email claim, or frontend mock.
- Document Google Cloud OAuth-client setup and a clear, safe local launch command. Keep `./sigma start` unchanged unless the user explicitly chooses real Google mode. Rename/introduce `--mock-cloud` for simulated mode, with `--admin` retained temporarily as a compatibility alias. Do not require real credentials for mock mode.
- **Bootstrap admin:** `SIGMA_CLOUD_BOOTSTRAP_ADMIN_EMAIL` is the operator's **actual Google account email**, supplied through protected configuration, not committed to the repo. On first verified login, the auth database binds that email to Google's immutable verified `sub` and grants `admin`; on subsequent logins require **both** matching email and bound subject. Bootstrap administrator cannot be revoked through ordinary Access Management. A nonmatching account must not inherit admin privileges.
- Local versus hosted state: a real local login must clearly indicate which administration target it operates on. **Do not claim local edits administer the hosted service if they only touch local SQLite.** For actual hosted administration from the local app, use a separately authenticated, HTTPS, server-authorized admin API/session against the hosted service (never direct remote SQLite/filesystem or copied cookies); if this secure routing is not implementable within this ticket, mark it UNMET and do not present a fake shared admin state. Preserve local SIGMA project behavior and cloud workspace isolation.
