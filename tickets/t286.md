# Issue #286 — Maximum Concurrent Sessions

## Scope

Add **Maximum concurrent sessions** to **Project Settings → Limits**. The
application-code default is **1**. Accept every positive integer without an
application-defined upper bound. The setting is per project, persisted with
project limits, and preserved through JSON project export/import.

Enforce the setting server-side and atomically across concurrent callers and
processes. Increasing the limit allows starts immediately. Decreasing it leaves
existing sessions running and blocks new starts until active sessions are below
the new limit. Completed, stopped, failed, paused, and safely recovered
interrupted sessions release their slots. Ambiguous dispatched provider calls
must not be replayed automatically. Show an actionable capacity error in the
existing Limits UI.

## Acceptance

- New and legacy projects default to one; reject zero, negative, fractional, and
  malformed values.
- Save/load, project isolation, and JSON bundle round-trip preserve the value.
- A concurrent start race never exceeds the configured per-project count.
- Session lifecycle and crash recovery release capacity safely.
- Run backend checks, `./sigma test`, frontend typecheck/build, and real-Chrome
  Limits acceptance. No paid calls or production deployment.
- Submit an isolated branch PR for independent review; do not self-merge.
