# T26 — SageMath execution for research agents

**Owner:** Green (Codex). **Status:** Ready for implementation; not started.
**Recommended model:** Current Green default, Medium thinking; escalate only for a concrete integration/security obstacle after discussion.
**Dependencies:** T18 orchestration, T19 Python sandbox, T24 outcome metrics/provenance.

## Goal

Provide SageMath as a first-class, agent-aware computational tool at the **same support level as scientific Python**. SageMath execution must be available to research agents for exact algebra, number theory, symbolic computation and other Sage facilities. It must not be confused with mathematical proof verification.

## Required behavior

1. **Discoverability is mandatory.** The coordinator's instructions/context for **every participating research agent** must explicitly enumerate the available execution tools, including SageMath, how to request a Sage computation, its relevant capabilities and limits, and how to interpret results. This includes Investigator, Skeptic and any additional participating roles. Do not rely on one agent relaying this knowledge to another. When unavailable, report that truthfully rather than advertising a working tool.
2. Add a typed SageMath execution request/result path integrated with the existing Investigator → execution → Skeptic workflow, session state and agent handoffs. Avoid overloading a Python-only field with ambiguous semantics. Retain the existing Python workflow unchanged.
3. Support agent-authored Sage code in an isolated, pinned, reproducible SageMath runtime. Mirror T19's controls: no execution-time network, no host/project/credential mounts, non-root, read-only root filesystem, no added capabilities, no-new-privileges, bounded wall time/CPU/memory/processes/writable space/source/output and cancellation. No runtime image pull/build.
4. Persist source, execution ID, runtime/version, exit status, stdout/stderr, captured files/artifacts and project/session/strategy/cycle/agent provenance. Make all results available to the Skeptic and subsequent authorized research context, including errors and limitations. Failed, interrupted and timed-out runs must never be represented as successful evidence.
5. Integrate Sage executions with T24 operational metrics, artifact counts, and provenance without double counting. Preserve bounded call budgets and no automatic provider retries or billing fallback.
6. Keep setup and testing practical: reproducible image build/setup via the SIGMA tooling; clear unavailable-runtime guidance. Avoid forcing all developers to download a large Sage image when Sage support is not needed, unless justified and agreed.
7. Explicitly distinguish Sage's symbolic/exact computations from formal proof checking. No claims of theorem verification based only on a Sage result.

## Acceptance and tests

- Unit/contract tests for tool advertisement to **each** agent role, including available/unavailable states, and an agent request that selects Sage instead of Python.
- End-to-end deterministic Investigator → Sage → Skeptic scenario showing source, result and provenance preserved across a session and later retrieval.
- Real isolated Sage container smoke tests for symbolic algebra and number theory, captured artifact, failure, timeout, network denial, resource limits and cancellation.
- Regression tests for ordinary Python execution and existing research sessions; no accidental changes to agent budgets or persisted legacy records.
- Run `./sigma test`, relevant browser/CLI scenarios, and document exact results and unrun checks. No paid live-provider calls without explicit approval.
- Green opens a PR, supplies evidence and limitations, and does not self-merge. ChatGPT reviews integration and merge.

## Scope boundary

No Sage-specific UI redesign in T26. Expose capability and evidence through existing research/session/artifact surfaces; any substantial new UI is a separate Gray ticket.
