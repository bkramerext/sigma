# T22.3 — Cloudflare provisioning and hosted release

Status: SPECIFIED, provisioning NOT STARTED. Parent: [T22](t22.md). This is the executable deployment and acceptance checklist, not a replacement for parent T22 requirements.

**Alpha scope:** Automated backups, off-host backup infrastructure and restore drills are deferred by the human. This alpha may lose data after host or volume failure; disclose this limitation. Persistence across ordinary restart/redeployment, research recovery, isolation and safe rollback remain mandatory. Follow-up: [T22.4 Cloud backups and tested restoration](t22.4.md), required before beta/production or irreplaceable research data.

## Ownership and constraints

- ChatGPT cloud coordinator owns specification, priority, PR/requirement reviews, integration acceptance, and final release recommendation.
- Red owns deployment engineering, scripts/config, runbook, deterministic hosting tests, and implementation of approved provisioning steps. Red's existing cloud deployment assignment remains active; no duplicate assignment is implied.
- Green owns T22 Gate B research execution, durable job accounting, cloud model credential use, and sandbox controls. Red must not change Green's engine. Dependencies route through coordinator/human.
- Human controls Cloudflare and backend account creation, subscriptions, purchases, credentials, domain/DNS changes, and final external publication/signoff.
- No purchased services, domain purchases, live provider spend, external publication, or unsafe credential handling without explicit human permission. Keep local operation independent of cloud infrastructure.

## Exit criteria

A real service is reachable through a Cloudflare-managed HTTPS endpoint with functioning Google OIDC, isolated private workspaces, public read-only Demo, durable bounded research, persistent storage, safe restart/redeployment, and rollback. All parent T22 gates and the integrated release gate pass. Production-ready artifacts and mocked tests alone are NOT actual deployment or T22 completion.

## D1: Hosting decision and cost/provisioning inventory

- Read T22.1 feasibility findings. Adopt the selected Cloudflare/hybrid approach unless concrete deployment evidence requires changing it; record any changed rationale.
- Specify frontend delivery, Cloudflare DNS/TLS/proxy or Workers routing, persistent Python backend/worker host, SQLite/project data storage, job execution and Python/Sage sandbox host. Do not run a long-lived Python service on an ephemeral Cloudflare Worker filesystem.
- Produce concrete provider/plan/region selections, sizing, networking, TLS/origin reachability, domains (workers.dev/test hostname initially; custom domain optional), least-privilege IAM/API tokens, persistent storage locations, and responsible operator accounts.
- At the time of purchase, verify current pricing and limits from authoritative providers; document free versus paid requirements and estimated monthly baseline versus variable compute/storage/network/model charges, plus configurable spending ceilings. Do not invent prices or assume free tiers satisfy durability.
- Deliver an itemized list of user actions/approvals for account registration, billing, DNS, OAuth setup, backend host and provider keys. No unapproved charge.

## D2: Deployable, reproducible infrastructure (Red)

- Implement repository-managed deployment config/scripts for frontend, Cloudflare routing/TLS, Python API/worker, persistent mounted volumes/databases, startup/readiness/health, secret injection, access-control-safe logs and rollback. Pin/record deploy version and provide reproducible clean-host steps.
- Persist auth DB, identity/workspace mappings, user project trees, sessions/jobs and call reservation ledger, artifacts, audit files, and rate/budget state in appropriate persistent storage. Ensure service UID/GID/permissions and filesystem roots remain stable across reboot/redeploy.
- Install `SIGMA_CLOUD_DEMO_AUDIT` as reviewed fixed curated file outside private roots, with safe service ownership and write permissions. Never publish any user's project as Demo.
- Configure approved Google client ID/secret/redirect URI and `SIGMA_CLOUD_PUBLIC_ORIGIN`; set cookie security, CSRF/origin checks, CORS, trusted hosts, HTTPS redirect, security headers, secrets rotation and private network exposure limits.
- Cloud server credentials must not fall back to a local ChatGPT account or key; no keys in repository, frontend bundle, exported artifact, or logs. Gate B per-user/global budgets must fail closed.
- Supply versioned migration, data-safe redeploy, service restart and rollback steps. Failure to obtain required state/storage should fail closed instead of starting a fresh empty workspace.

## D3: Operability and recoverability (Red)

- Supply concise deployment/operations runbook with exact commands for initial provision, first admin authorization, regular deploy, diagnostics, restart/recovery, rotation, compromise containment, guest exposure shutdown, inference kill switch, and rollback.
- Demonstrate that normal service restart and versioned redeployment preserve auth mappings, two users' private projects and artifacts, durable research job/cost state, and permission boundaries. Scheduled backups, off-host recovery and restoration drills are explicitly deferred for this external-evaluation alpha.
- Provide logs/health/alert checks sufficient to detect auth failures, unauthorized requests, job/restart problems, budget denials, and backend outages without leaking secrets or private content.
- Make local mode, `./sigma start`, `./sigma shutdown`, `./sigma test`, and existing project files unaffected.

## D4: Actual provisioning (requires human authorization)

- Obtain explicit operator decisions/permissions for Cloudflare account/plan, backend hosting provider/plan, spending caps, test URL/domain and DNS changes. Do not assume Cloudflare has been purchased, configured, or deployed.
- Create infrastructure only after those approvals. Configure cloud service identities and secrets securely through provider dashboards/secret stores; never request raw secrets be pasted into chat or committed to Git.
- Deploy to a controlled HTTPS test endpoint, exercise genuine network routing to backend, verified Google OAuth redirect, email/domain authorization, denied account, administrator functions, logout and revocation. Remove any temporary broad gmail.com domain authorization before external launch.
- Ensure startup creates no accidental public writable area and that guest Demo still works when provider inference is disabled.

## D5: Acceptance matrix, exercised on actual deployed stack

For every check record date, deployed commit, sanitized config, identity fixture, commands, observed outcome and MET/UNMET/UNVERIFIED:

1. Anonymous visitor opens actual HTTPS /demo, sees saved project/strategies/session/outcome/evidence and downloads JSON/TXT/HTML/TEX through unmocked backend; guessed private paths, guest mutation, agent and export endpoints fail.
2. Authorized Google account A signs in, creates private project, runs bounded research with a deterministic fake provider, disconnects/reconnects browser, observes progress/results, exports and signs out to guest Demo.
3. Account B cannot read/change/run/stop/export A's resources even with copied IDs/URLs; revoking A terminates new access promptly; bootstrap admin manages access but cannot silently browse private research.
4. Hard backend restart/redeploy during queued/running jobs preserves durable state, accounting, and artifacts. Ambiguous provider attempts are marked unknown and never blindly replayed. Duplicate requests cannot create duplicate billable dispatch.
5. Concurrency/queue, time/call/token/cost caps are enforced under parallel requests; missing credentials/limits fail closed. Python/Sage execute only in the documented isolated bounded environment with no default network.
6. Restart and redeploy the service without replacing persistent volumes; validate auth mapping, workspaces, job ledger, budgets and artifacts before and after. Exercise rollback against the same persistent state without unintended deletion.
7. Check production HTTPS headers, secure cookies/CSRF, DNS/TLS routing, secrets not visible in bundles/exports/logs, non-root service boundaries, error messages and basic operational logs.
8. Full `./sigma test`, production-mode API security tests and true browser-to-backend E2E. UI-only mocked routes count only toward separate frontend checks.
9. Live paid provider smoke is *separate*, requires explicit human approval of credential and maximum spend, and must report actual charges/unknowns, not treat estimates as invoices.

## Sequence and gates

1. **Preparation:** Red delivers D1–D3 in PR with handoff; coordinator reviews/merges, Gate B must independently merge.
2. **Integration:** Combined A+B+C and deployment setup are regression-tested on `main` before cloud provisioning; coordinator logs remaining risks.
3. **Account/payment checkpoint:** human explicitly approves actual providers, spend, credentials and test endpoint; no automatic purchases.
4. **Controlled hosted trial:** Red implements D4 and runs D5 with deterministic fake providers; coordinator audits evidence.
5. **Public launch checkpoint:** human explicitly approves exposure to external mathematicians only after no mandatory security/tenant isolation/durability/budget failures remain; document known limitations.
6. **Exit:** parent T22 only closes after deployed acceptance and operational runbook, not merely because the feature PRs merged.
