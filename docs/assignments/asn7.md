## 1. Strategies surface and rows

- Rename all visible **Strategy Pool / Strategy pool** terminology on the project workspace to **Strategies**. Retain existing strategies, operations, events, and history; avoid gratuitous wholesale renaming of internal identifiers or APIs where no benefit.
- Present each **actual** strategy as a compact row with a prominent title and **one-line smaller, subdued description** (a faithful summary/preview of the real approach). Do not fabricate descriptions or truncate stored content. If a reliable preview cannot be derived from the full approach, support a persisted optional one-line summary with sensible legacy fallback. Full approaches must remain available through an intuitive, accessible row detail expansion or equivalent real action, without requiring edit mode. Longer rows/mobile text must not overflow or hide information permanently.
- Show actual persisted strategy metadata, including distinguishable provenance when it is AI-assisted. Stable reference labels may be derived from real identity/order, but **never invent** arbitrary `S-042`-style research IDs. If no meaningful short reference exists, omit that column or use an honest compact ID.
- Keep currently working edit, remove, project-history retention, loading/errors, Open/Close, route navigation and responsive behavior.

## 2. Menus and persisted drag ordering

- Replace the current strategy-name **chevron** disclosure trigger with a compact accessible **vertical three-dot** control in each row. The menu must expose actual working edit/remove actions and preserve truthful disabled/future functions where applicable. Keep keyboard opening, one-menu-at-a-time behavior, outside-click dismissal, Escape, focus return, nested-group semantics when retained, and legibility. Do not preserve the old chevron as a duplicate.
- Remove **Promote** and **Demote** from the visible command structure. Strategy priority/order is controlled by the **upper-right corner grip** from the approved mock. The grip should visibly suggest dragging without competing with the three-dot control; do not make the entire row drag-active (users must be able to select text and open details).
- Implement real pointer/touch **drag and drop** to reorder active strategies, with clear lifted/target/settled feedback; persist order to the project. Refresh/reopen must keep it. Handle failed saves by reverting UI and showing a useful error. Don't silently reorder due to an uncommitted drag; support cancellation.
- Provide an equally capable **keyboard-accessible** reorder interaction associated with the grip (e.g., Space to pick up, arrows to move, Enter to drop, Escape to cancel), with announcements/instructions. Do not reintroduce Promote/Demote as a substitute for the visible drag design.
- Respect removed strategies and history. Preserve stable strategy identities, creation timestamps and order when editing/removing; define how new strategies join the list. Ensure atomic/concurrent persistence under existing storage guarantees. Tests must cover legacy order, active-only reorder, reload, errors and races.
- Avoid heavy drag libraries if native/pointer handling suffices, but prioritize real cross-device behavior over library avoidance. Browser-native HTML drag alone does not reliably cover mobile touch; actually test touch interactions.

## 3. Honest stages / progress indicators

- The mock's colored circular stage markers are **descriptive stage labels, not percentage-complete bars**. Implement an explicit, persisted per-strategy stage that tells the truth about work recorded in SIGMA.
- This release has **no strategy runner, evaluator or formal proof checker**. Therefore no strategy may appear as automatically `Investigating`, `Evidence review` or `Evaluated` merely because the mock shows those labels. Do not create fake activity, timestamps or claims of validated research.
- Provide a practical minimal **human-maintained** stage set, such as `Draft`, `Ready to explore`, `Exploring` (meaning the human is actively investigating, **not** that an AI agent is running), and `On hold`. New/legacy strategies should have a conservative truthful default, e.g. `Draft`. Expose a clear explicit action to change the stage, track the change in durable project history, and label/describe these as **manually tracked**. Reserve automation-driven/evidence-complete states until substantiating functionality exists.
- Distinguish stages using text plus subtle colored rings; never color alone. Treat mock colors as a design palette, not proof of statuses. Legacy files must load without rewriting until an actual update.

## 4. New Strategy: two intentional routes

- Implement the exact split/dropdown **New Strategy** command style from the approved workspace mock: **Write manually** and **Generate with AI**. Make the choice understandable and accessible. The primary click may use the preferred/default mode if clear, with the adjacent arrow revealing both options. Do not keep duplicate prominent buttons that fight the approved composition.
- **Manual:** Retain the existing title + full approach workflow with real validations and persistence. Adapt its visuals to the new layout and support a one-line preview as needed. Manual creation remains fully functional even when no AI is configured.
- **AI:** Open a coherent dark/copper **Generate a strategy** dialog: explain that SIGMA proposes **one** distinct research direction and the person reviews/edits before saving. Include an optional multiline **Starting point** (or **Seed idea**) described as a hunch, question, technique, observation or constraint. Leaving it empty asks the model for an independent direction. This idea informs exploration; it is **not** an instruction to uncritically endorse an assumption.
- Context for generation: actual project research problem, research mode, existing strategies (enough title/approach to avoid duplicate directions), and optional seed. The UI should truthfully indicate what context will be sent. A prior exploratory AI dialog mock is available from the design conversation as *guidance*; the **workspace mock** is the explicitly approved visual contract.
- Model response: one well-developed, **distinct** proposal with a concise title, a helpful one-line preview, a substantive proposed approach and concrete first tests / assumptions / ways the line might fail. Prefer discriminating mathematical content over generic exhortations or relabeling existing strategies, particularly in mathematical mode. Don't assert unproved statements as theorems.
- Present response as **editable draft fields**; clearly distinguish `Generate draft`, `Regenerate` (explicit new paid request), `Save strategy` (the only creation/persistence action) and `Cancel`. Do **not** auto-save, run agents, create a batch, schedule research, evaluate proofs, or mutate project data on generation, retry, failed call or dialog close. Avoid leaving background requests running after explicit cancellation if cancellation is supported.
- Store the accepted proposal with truthful provenance (manual vs AI-assisted suggestion **accepted/edited by a human**); keep original human-owned workflow and backwards compatibility. Include at least model/provider identity metadata if returned and useful, without storing API keys or confidential request dumps. Clearly distinguish drafts not yet accepted from saved strategies.
- Handle provider unavailable, malformed output, duplicate/repetitive proposal, timeout, network failure, retries, simultaneous requests, and user cancellation gracefully. Preserve edited text through recoverable failures. Enforce length bounds server-side, validate model output, and never execute generated text as commands.

## 5. Minimal real AI integration

- This must call a **real configurable model API**, not a mock response posing as AI, and must be an opt-in action initiated by the user. Use an isolated Python backend provider adapter/service; do not send credentials from the browser. Choose one supported initial provider (OpenAI API is a reasonable starting point) and document precisely how to configure the model and key with environment variables. Do not assume a ChatGPT subscription or Codex allowance includes API credits; external API calls may incur separate usage charges.
- Keep model choice in **server-level configuration for now**, e.g. environment variables with a documented default and clear validation. **Project-level thinking/reasoning effort belongs in a later configuration assignment; do not implement it here.** Do not add project settings UI simply because the mock shows a gear icon.
- Structure generation with a strict validated schema and bounded output; limit contextual payload deliberately, never silently drop critical constraints, and respect hard request timeout and single-request concurrency rules. Provide server-side failures rather than hallucinated fallback success. Use supported SDK/API semantics appropriate to the selected provider, pin/document dependencies and use mockable service boundaries.
- Disclose explicitly before first generation that project problem, existing strategies and optional seed are transmitted to the configured model provider. Do not make outbound calls on page load or while typing. Avoid logging prompts, model outputs or secrets by default; prevent credentials from entering Git or browser bundles.
- Document expected API billing and simple operational limits (one result per click, bounded context/output and timeout). No autonomous loops, tool invocation, RAG/web research, background queues, system-wide scheduler or long-running agent orchestration.
